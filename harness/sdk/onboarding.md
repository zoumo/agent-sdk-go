# 新 Agent 的 SDK 接入流程

## 使用方式

接入者先读取[通用架构](architecture.md)和[共同用户故事](user-stories.md)，再执行本流程。必需能力由仓库共同合同决定，不能由某个接入方重新选择。流程产物应保存在对应项目约定的位置；本规范不绑定具体协议、工具、目录布局或现有实现。

## 阶段与完成条件

| 阶段 | 输入 | 工作与产物 | 完成条件 |
|---|---|---|---|
| 1. 确认共同合同 | 架构、术语、全部共同故事 | 建立覆盖全部故事的接入清单，记录需要澄清的共同合同问题。 | 每个故事都有验收目标；没有自行缩减必需能力。 |
| 2. 调研并固定原生基线 | 目标运行时及官方资料 | 检查协议、官方实现与测试、许可证；固定版本、源码提交、原始文件哈希与引用，区分声明和已观察行为。 | 关键协议依据可追溯、可重取；资料版本没有混用，使用与分发边界明确。 |
| 3. 映射能力与缺口 | 固定基线、接入清单 | 为每个故事填写原生依据、对外操作、条件、差异、缺口和计划证据；覆盖生命周期、输入、控制、事件、历史、观察及子 Agent 列举。 | 所有目标都有映射；未知或不支持明确记录，没有用推测填补原生语义。 |
| 4. 设计原生适配 | 能力映射 | 定义身份、事件与未知数据、原生类型来源、交互句柄、资源所有权、错误、取消、结束和 Load 合同；明确统一操作如何映射。 | 成功与失败的含义可检验；不引入隐式调度、自动恢复或无依据的关系和权限。 |
| 5. 建立最小闭环 | 适配设计、协议类型 | 实现建立交互、初始化、输入、事件、结束及资源清理；以离线原生对端贯穿公开路径。 | 能完成一次交互并继续下一次输入；拒绝、故障和清理结果可观察。最小闭环不表示完整接入。 |
| 6. 实现共同能力 | 最小闭环、全部故事 | 完成审批与问答、配置控制、中断、子 Agent 自动观察和列举、显式 Load 等共同目标；补充原生扩展。 | 能力清单与公开行为一致，已知不支持明确拒绝，必要故事没有因实现困难被删除。 |
| 7. 执行分层验证 | 实现、映射、协议样本 | 运行共同验收及协议、故障、并发、资源、回放检查；按授权范围补充真实验证，记录结果及限制。 | 必需验收没有未处理失败或被跳过的缺口；源码、合成、录制和真实运行的结论分开。 |
| 8. 验证交付 | 验收证据、可分发产物 | 从独立消费者检查公开操作、示例和分发完整性；核对许可证、版本、能力说明及发布要求。 | 对实际交付版本验证成立，外部使用路径可重现；发布状态和兼容性结论有相应证据。 |

## 调研重点

原生合同至少需要回答下列问题，缺少依据时记录未知：

- 建立交互需要哪些初始化、认证和版本条件？会话身份由什么确认？
- 输入提交成功证明到哪一步？执行中输入如何处理，是否有明确调度选项？
- 哪些事件表示结果、状态或失败？哪些关联身份、未知字段和原始数据需要保留？
- 如何取得审批或问答的原始请求？如何回答、取消、判断失效和不确定结果？
- 模型及思考配置能否创建时选择或动态修改？响应证明的生效时机和作用范围是什么？
- 如何确认子 Agent 属于观察范围、订阅其事件并查询已有成员？缺失父级、分页和存储访问如何表示？
- 中断影响什么？谁拥有进程或连接，关闭、退出和清理完成分别如何观察？
- 断线后哪些事实仍可确认？不依赖自动重连时，怎样显式恢复同一会话并加载保留历史？
- 历史保留了什么、遗漏了什么？加载完成或部分失败如何表达，怎样避免回放触发执行或审批？
- 慢消费、超大消息、重复请求、并发与资源超限会产生什么可观察结果？

## 交付物检查清单

- [ ] 共同故事全部进入能力映射，缺口及条件明确。
- [ ] 原生版本、协议来源、哈希、许可证与使用范围可追溯。
- [ ] 对外操作、事件、身份、回答权限、资源所有权及错误语义有合同。
- [ ] 最小闭环和完整能力分别验证，示例使用公开操作。
- [ ] 共同故事与原生特有行为都有相应证据，没有用跳过或合成证据冒充真实通过。
- [ ] 历史与实时证据可区分；断线不自动恢复，Load 不承诺重建遗漏的实时事件。
- [ ] 子 Agent 的观察与列举均覆盖，成员、父级、活跃状态和订阅状态没有相互冒充。
- [ ] 外部消费者及实际交付版本验证可重现，能力说明与证据一致。

遇到原生协议无法满足共同合同的情况，先保留明确缺口，再修订适配方案或共同合同。不能通过隐藏错误、补造证据、隐式替换原生操作或修改验收预期来完成接入。
